# DeckForge — Complete Requirements & Phased Roadmap
### Working title. "Vibe" is banned from this project.

**What it is:** A split-screen gamepad-only interface for Claude Code on the Steam Deck. Left panel shows raw Claude Code terminal (read-only). Right panel is an LLM-generated prompt engineering tree navigated with ABXY. The user is the creative director — steering, not driving. It's a way for software engineers to dive into their creativity and make fun shit in a way they've never experienced before.

**What it is NOT:** "Vibe coding." It's not lazy or low-effort. It's a deliberate, opinionated interface that forces plan-mode thinking through constrained input. Every button press is a creative decision.

---

## PHASE 0: Foundation (non-negotiable core)

Everything here must work before anything else matters.

### 0.1 Claude Code Subprocess
- Spawn Claude Code headlessly via `claude-code-sdk-python`
- Stream JSON output in real-time to left panel
- Send prompts programmatically (the user never types into Claude Code)
- Handle session resume/persistence per project
- Auto-commit after every completed task (git-backed undo). Commit message = plan summary from prediction engine (tagged `[DeckForge]` for feature detection)
- **System prompt injection** via SDK's `system_prompt` parameter with `append` mode:
  - Keeps Claude Code's default behavior
  - Appends DeckForge-specific instructions: "The user strongly prefers not to type — handle everything yourself. They CAN use a keyboard but it's a last resort. Provide clear progress updates. This project is controlled via a gamepad interface."
- **Per-project CLAUDE.md** auto-generated by DeckForge in `.claude/CLAUDE.md`:
  - Build/run commands (detected or user-configured)
  - Tech stack notes
  - Project-specific conventions
  - Loaded via `setting_sources: ["project"]`
- **Permission mode:** `acceptEdits` + granular `allowed_tools` (auto-approve file edits, specific bash patterns like `git *`, `npm *`). Custom permission callback for dangerous operations (DeckForge shows a gamepad-friendly confirmation on the right panel instead of Claude Code's default terminal prompt)

### 0.2 Split-Screen Layout
- Left panel (default 55%): Raw Claude Code terminal output, read-only, scrollable (R-stick)
- Right panel (default 45%): DeckForge interface (action palette, status, plans)
- **User-configurable split ratio** with gamepad-friendly resizer:
  - Hold LB + D-pad left/right to nudge the divider (5% increments per tap, smooth scroll if held)
  - Visual divider bar glows/highlights when in resize mode so user knows it's active
  - Snaps to presets at 30/70, 40/60, 50/50, 60/40, 70/30 (D-pad up/down to jump between presets)
  - Saved per-project (some projects you want more terminal, some more interface)
  - Min 20% / max 80% on either side (never fully hide a panel)
- 1280x800 resolution (Steam Deck native)
- Terminal/hacker aesthetic (dark bg, green/amber accents, monospace)
- Scanline overlay for flavor

### 0.3 ABXY Action Palette (The Core Interaction)
- Level 1 categories: A=Feature, B=Bug, X=Tech Debt, Y=Yolo
- Level 2: LLM-generated options per category (A/B = sensible suggestions, X = reroll with modifier, Y = chaotic/fun option)
- Level 3: Plan confirmation (A=Ship it, B=Reject, X=Tell me more, Y=Ship it but unhinged)
- D-pad navigation for scrolling additional options beyond ABXY
- RB = Reroll all suggestions
- **Y is ALWAYS something ridiculous.** This is a design rule, not a suggestion.
- Every option has a personality one-liner generated by the LLM

### 0.4 Plan Mode (the whole point)
- Every action goes through plan confirmation before AI starts coding
- User sees numbered steps, estimated time
- A = approve, B = reject, X = expand details, Y = approve with extra creative freedom
- Plan visible on right panel while Claude Code thinks on left

### 0.5 Gamepad Input
- Read Steam Deck buttons via evdev/SDL
- D-pad, face buttons (ABXY), triggers (LT/RT), bumpers (LB/RB)
- 4 back grip buttons (L4/L5/R4/R5) — configurable per project
- Sticks for navigation and scrolling

### 0.6 Window Switching
- RT = Switch to app being built (fullscreen, DeckForge yields focus)
- LT = Switch back to DeckForge
- Implemented via wlrctl (Wayland) with wmctrl fallback (X11)
- Track window IDs of both DeckForge and the launched app

### 0.7 App Launcher (app-type agnostic)
- Auto-detect run command: package.json scripts, Makefile, main.py, index.html, .godot, etc.
- First-time launch config screen if auto-detect fails
- Save run command per project
- Kill/restart app process cleanly

### 0.8 Project Management
- Create new projects (voice pitch → Claude Code init)
- Resume existing projects (session restore)
- Project list with git status
- Delete projects (with confirmation)

## PHASE 1: Essential UX

Makes the app feel complete and polished.

### 1.1 Screenshot Feedback Loop
- RB captures screen (scrot/grim, works on any window type)
- Freeze + flash overlay
- A = send screenshot to AI context silently
- Optional voice annotation (high friction: LB+A combo)
- Screenshot + annotation can trigger a new task

### 1.2 QA Mode
- Menu button triggers QA
- AI autonomously tests the app (launches, interacts, screenshots, compares)
- QA report with pass/fail per feature
- Each failure is a selectable "fix this" action
- "Fix all" option for lazy trust
- Returns to main loop after fixes

### 1.3 History / Undo
- View button opens git-backed timeline
- Every AI action is a commit
- D-pad to scroll, A to preview state, Y to rollback
- Rollback confirmation screen (shows what will be undone)

### 1.4 Microphone Input (SAFETY HATCH ONLY)
- High friction: LB + A combo (not single button)
- Only offered in specific contexts (Bug mode "I'll describe it", "Something else?" last resort)
- whisper.cpp or Vosk for local/offline transcription
- Should feel like pulling an emergency brake
- **Design rule: if users are using the mic frequently, our predictions are failing**

### 1.5 Voice Pitch for New Projects
- "What are we building?" screen for new projects
- Hold LB+A, speak, release to transcribe
- Show transcription, A to confirm, B to re-record
- This is the ONE place where voice is expected and encouraged

### 1.6 Error States
- Global error screen for: Claude Code crash, build failure, network drop, voice failure
- Recovery options: Let AI fix, rollback, retry, main menu
- Error messages have personality too

### 1.7 Deploy Mode
- Dedicated screen for pushing code to remote and triggering deployment
- Split-panel layout: terminal shows git status, commit log, pre-flight checks, deploy config; right panel shows deploy actions
- Pre-flight checks: tests passing, no lint errors, TypeScript clean, bundle under budget, no merge conflicts
- **A = Push and Deploy** — merge to target branch, push to origin, trigger production deploy
- **B = Preview Deploy** — push branch, deploy to temporary preview URL, no merge (non-destructive)
- **X = Push Only** — push branch to origin, open a PR, no deploy trigger
- **Y = Review Changes** — view full diff of all commits before deciding
- **RB = Change Deploy Target** — switch between configured providers (Vercel, Railway, Netlify, GitHub Pages)
- **LB = Deploy History** — view past deployments with status and URLs
- Supports multiple deploy providers per project (configured in project settings on first deploy)
- Auto-detects deploy config from existing `vercel.json`, `railway.toml`, `netlify.toml` if present
- Shows live deploy status in terminal after push (polling deploy provider API)
- **Design rule:** This is the payoff screen. Greenfield to `myapp.vercel.app` without touching a keyboard. The whole product story lands here.

## ARCHITECTURE: DUAL-LLM SYSTEM

DeckForge has **two separate LLM integration points.** This is a critical architectural decision.

### The Coding Engine (Left Panel)
- **What:** Claude Code subprocess via `claude-code-sdk-python`
- **Role:** Takes approved plans and writes code. Reads codebases, edits files, runs tests, fixes errors.
- **Characteristics:** Heavy, stateful, session-persistent, context-window-managed
- **When it runs:** After plan approval (Level 3 → "Ship it")
- **The user never interacts with Claude Code directly.** DeckForge sends it prompts programmatically.

### The Prediction Engine (Right Panel)
- **What:** Direct LLM API calls (Anthropic, OpenAI, or Gemini — configurable)
- **Role:** Generates action palette suggestions, quirky one-liners, bug predictions, feature ideas, plan summaries, QA analysis suggestions, exploration mode content
- **Characteristics:** Lightweight, stateless, fast, cheap. Can use smaller/faster models (Haiku, Gemini Flash, GPT-4o-mini)
- **When it runs:** Every time the user enters a new screen that needs generated options (Level 2 suggestions, plan details, QA reports, exploration ideas)
- **Context:** Receives project metadata (file tree, detected features, recent git log, current errors) as structured context — NOT the full Claude Code conversation

### Why Two Systems?
1. **Speed:** Prediction calls return in <1s using fast models. Claude Code is slower by design (it's doing real work).
2. **Cost:** Feature suggestions don't need Opus. Haiku or Flash is fine.
3. **Clean context:** Claude Code's context window stays focused on coding, not cluttered with "generate 4 feature ideas" back-and-forth.
4. **Flexibility:** User can pick their preferred prediction model (or we can A/B test which model gives the best suggestions).
5. **Separation of concerns:** Creative generation ≠ code generation. Different problems, different tools.

### What Gets Sent to Each System

| Data | Coding Engine (Claude Code) | Prediction Engine (Direct API) |
|------|---------------------------|-------------------------------|
| Full codebase context | ✅ (reads files directly) | ❌ (gets summary only) |
| Approved plan text | ✅ (this is its prompt) | ❌ |
| Project file tree | ✅ | ✅ |
| Detected features list | ❌ | ✅ |
| Recent git log | ❌ | ✅ |
| Current errors/warnings | ❌ | ✅ |
| Screenshots | ✅ (via context) | ✅ (for QA analysis) |
| User's past choices | ❌ | ✅ (for better predictions) |

## TECHNICAL STACK

| Layer | Choice | Why |
|-------|--------|-----|
| Coding engine | claude-code-sdk-python | Official SDK, JSON streaming, subprocess, system prompt injection |
| Prediction engine | Direct LLM API (Anthropic/OpenAI/Gemini) | Fast, cheap, stateless suggestion generation |
| UI shell | Tauri 2 + Svelte | Lighter than Electron. Svelte chosen for AI-codability: closest to plain HTML/CSS, minimal footguns, mockups translate 1:1 |
| Backend API | FastAPI on Railway | Proxies prediction calls, logging, prompt management |
| Observability | Langfuse (self-hosted on Railway) | Open source, RLHF dataset export, A/B testing, ~$15/mo |
| Database | PostgreSQL (Railway) | Langfuse storage, user accounts, project metadata |
| Gamepad input | SDL2 / evdev | Direct hardware access on Linux |
| Speech-to-text | whisper.cpp (tiny model) | Proven on Steam Deck, offline |
| Screenshots | pyscreenshot | Wayland + X11 compatible |
| Window management | wlrctl + wmctrl | Wayland-first, X11 fallback |
| Packaging | Flatpak | Steam Deck native |

## DESIGN RULES (non-negotiable)

1. **Y is always ridiculous.** Every screen, every level. This is the soul of the app.
2. **Mic is a safety hatch.** High friction (LB+A). If users need it often, our predictions suck.
3. **Every option has personality.** One-liner quips on everything. Pre-written, not generated.
4. **Plan mode is mandatory.** Every action goes through plan confirmation (except Yolo).
5. **Split-screen always.** Left = Claude Code, Right = DeckForge. The user sees the code.
6. **App-type agnostic.** People build games, desktop apps, CLI tools — not just web apps.
7. **The word "vibe" does not exist in this project.**
8. **Fun is the point.** This app exists to make building software feel like play.
9. **Two brains, two jobs.** Claude Code writes code. A separate LLM generates predictions. Never conflate the two.
