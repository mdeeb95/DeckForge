D E C K F O R G E

Complete Screen Flow & State Diagram v0.2

Core Philosophy
> WHAT THIS APP ACTUALLY IS

DeckForge is a side-by-side prompt engineering agent that only takes ABXY inputs.

It is a cute way to force users into plan mode. The user picks from predicted actions (A/B/X/Y + D-pad), the AI generates a plan, the user approves or rejects, the AI codes. The user never types. They are the creative director — steering, not driving.

LAYOUT: SPLIT SCREEN

Left panel = raw Claude Code terminal output. Fully visible. The user CAN see the code flying by — they just can't interact with it directly. This is the "vibes" — watching the machine think. Right panel = DeckForge interface: action palette, status, plans, QA reports, personality. RT switches to the app being built (fullscreen). LT comes back.

MICROPHONE IS A SAFETY HATCH — NOT PRIMARY INPUT

If we're falling back to mic input, we've done something wrong. The predicted actions, back buttons, and ABXY must be good enough that voice is rarely needed. Voice input should feel like pulling the emergency brake — available, clearly labeled, but slightly inconvenient on purpose. High friction. Maybe a 2-button combo (hold LB + press A), not just a single hold. The goal: make the predictions so good that you NEVER need to speak.

PERSONALITY EVERYWHERE

Every screen has quirky, slightly sassy randomized messages. Inspired by Claude Code's "canoodling" / "cogitating" style. Splash screen welcome messages, project select flavor text, loading messages, empty state jokes, error messages with personality. This app should feel alive and fun. These messages are a huge part of the brand. We need an UNGODLY amount of them — hundreds per screen context. They should be written by a human, not generated on the fly.

TWO MODES: DEVELOPMENT + EXPLORATION

Development mode = the core loop (build things). Exploration mode = discover project ideas, browse templates, get inspired. Exploration is a separate flow, not just an action in dev mode. It's for when you sit down on the couch and don't know what to build yet.

Design Specification
> THE ACTION PALETTE: LLM-GENERATED PROMPT ENGINEERING TREE

The action palette is NOT a flat list of suggestions. It's a branching prompt engineering tree where each ABXY press drills deeper into specificity. The LLM generates most options dynamically based on project context. Y is ALWAYS something ridiculous.

LEVEL 1: Category

"What do you wanna do today?"

"what do you wanna do today?" [A] Feature "build something new" [B] Bug "fix something broken" [X] Tech Debt "clean up your mess" [Y] Yolo "let the AI cook"
Level 1 is mostly static categories. The taglines rotate with personality.
->A = Feature
LEVEL 2: LLM-Generated Options

"what kind of feature?"

"pick a feature, any feature" [A] Add dark mode "because of course" [B] Add search/filter "find your own notes for once" [X] Reroll "{with modifier}" [Y] Add a secret disco mode "why not?" -------- [D-pad down] More options... [RB] Reroll all
A, B = sensible LLM suggestions based on project analysis.
X = Reroll with modifier (cycles: "more ambitious" / "simpler" / "weirder" / "more useful").
Y = ALWAYS chaotic. The AI generates something fun/absurd. This is the soul of the app.
->A = dark mode
LEVEL 3: Plan Confirmation (S2.0b)

"here's my plan"

"ok I'll add dark mode" PLAN: 1. Add theme context 2. Create dark color palette 3. Add toggle in settings 4. Persist preference 5. Test both themes [A] Ship it [B] Nah, go back [X] Tell me more [Y] Ship it but make it unhinged
IF USER PICKED "Bug" (B)

Level 2: Bug Mode

"what's broken this time?" [A] AI-detected issue #1 "the save button doesn't actually save. ironic." [B] AI-detected issue #2 "dark mode makes text invisible. stealth mode?" [X] I'll describe it (voice input: LB+A) [Y] Fix everything "scorched earth debugging"
IF USER PICKED "Yolo" (Y)

Level 2: Chaos Mode

"you asked for it" The AI just... does something. No options. No plan review. It analyzes the project and adds whatever it thinks would be the most interesting. +------+ |ADDING| "adding personality | ... | to your app. don't | | worry about it." +------+ [B] STOP (only escape)
IF USER PICKED "Tech Debt" (X)

Level 2: Cleanup Mode

"time to adult, huh?" [A] Refactor messiest file "src/app.js is 400 lines. that's not a file, that's a cry for help." [B] Add tests "you have 0 tests. living dangerously." [X] Performance audit "make the fast thing faster" [Y] Delete unused code "marie kondo your repo"
ACTION PALETTE DESIGN RULES:

1. Y is ALWAYS chaotic/fun. Level 1 Yolo skips plan mode entirely. Level 2 Y options are absurd but buildable. Level 3 Y ("ship it but unhinged") tells the AI to add extra flair.

2. A and B are always sensible LLM-generated options. Context-aware, project-specific. The AI analyzes the codebase to suggest these.

3. X is meta/modifier. At Level 1 it's "Tech Debt." At Level 2 it's "Reroll with modifier." At Level 3 it's "Tell me more." It's the reflective button.

4. D-pad scrolls for more options beyond the 4 ABXY slots. But ABXY should be enough 80% of the time.

5. RB = Reroll all options. Regenerates the LLM suggestions. Good when nothing resonates.

6. Every option has a one-liner personality tagline. LLM-generated, slightly sassy. These are half the fun.

7. Bug mode auto-detects issues. The AI runs a quick analysis and surfaces known problems. The user doesn't have to describe bugs — the AI finds them.

8. Voice input (LB+A) is only offered in Bug mode's X slot ("I'll describe it") — the one case where you genuinely need to explain something the AI can't auto-detect. This keeps mic usage minimal.

Phase 3
> APP PREVIEW / LAUNCH MODE
CRITICAL DESIGN DECISION: App-Type Agnostic Launcher
People won't just build web apps. They'll build Pygame games, Godot projects, GTK/Qt desktop apps, CLI tools, Electron apps, Love2D games, Processing sketches — anything. DeckForge needs a flexible launch system, not "open a Chromium tab."

Approach: DeckForge manages app launch via a configurable run command (auto-detected or user-set). On RT, it runs the command, focuses that window via wmctrl/xdotool, and DeckForge yields focus. On LT, DeckForge reclaims focus. The app runs as its own native process — DeckForge never wraps or embeds it.

Auto-detection hierarchy: package.json scripts -> Makefile -> main.py -> index.html -> .godot project -> custom run command in settings.

The screenshot flow is critical. It's the primary way users give visual feedback. The optional voice annotation turns "here's what I see" into "here's what I see AND here's what's wrong." The AI receives both the image and the transcribed text.

Window management under the hood: DeckForge uses xdotool/wmctrl to track its own window ID and the app's window ID (captured at launch). LT = wmctrl -ia $DECKFORGE_WID, RT = wmctrl -ia $APP_WID. If app has crashed (window gone), RT shows S-ERR with "App not running — relaunch?" option.

> KEYBIND & INPUT CONFIGURATION
Steam Deck has 4 back grip buttons (L4, L5, R4, R5) that are fully programmable. Plus the trackpads can be configured as buttons on click. Discussion
> OPEN QUESTIONS & EDGE CASES
1. Predicted Action Generation
How many predictions? Fixed 6? Dynamic 4-10? How are they categorized? Do we group by type (feature / fix / style / test)?
2. Error States
What happens when Claude Code crashes? When the built app crashes? When voice transcription fails? Need error screens for each.
3. Mini-Game During Long Tasks (CONFIRMED)
While AI codes, an embedded mini-game is playable (pinball, snake, etc). Could even embed Steam games in a window later. Start/stop with memory management so it doesn't eat resources. This is the killer UX differentiator — you're literally gaming while coding.
4. Context Window
Claude Code has context limits. Do we surface "context is getting full" to the user? Auto-compact? Let them "forget" old features?
5. Multiplayer?
Could two Steam Decks collaborate on the same project? One person tests while the other directs the AI? Future feature but worth thinking about.
6. Templates
Pre-built starting points? "Blank canvas", "Simple game", "Drawing app", "Dashboard"? Speeds up the pitch phase.
7. Deployment (Mac to Steam Deck)
App runs in Steam Deck's Desktop Mode (KDE/Arch Linux). Build as Electron or similar, push to GitHub, clone on Deck. Could also package as a Flatpak for easy install. Claude Code already runs on Linux — just needs Node.js.
8. Plan Confirmation Step (CONFIRMED)
From Mathew's mockup: Every action goes through a "plan review" before AI starts coding. User sees numbered steps, can approve (A), reject (B), or voice-modify (LB). This is the key UX insight — control without typing.
